# Chain of Custody

Chain of custody is the chronological documentation that records the sequence of custody, control, transfer, analysis, and disposition of evidence. It is the foundation of forensic integrity.

## Core principles

1. **Every access is documented**. From acquisition to final report, every person who touches the evidence logs it.
2. **Hashes are timestamped**. Cryptographic hashes prove evidence hasn't changed between custody transitions.
3. **Tool versions are recorded**. A hash generated by `sha256deep v4.4` is different from `dc3dd v7.3.1`.
4. **No gaps in custody**. If evidence cannot be accounted for during any period, its integrity is compromised.
5. **Tamper-evident packaging**. Digital evidence should be sealed (encrypted containers, signed archives) before transfer.

## Custody log entries

Each entry must contain:
- **Timestamp** (ISO 8601, UTC preferred)
- **Action** — acquired, transferred, examined, archived, disposed
- **Operator** — name / identifier
- **Evidence item** — unique identifier (case_id + source_id)
- **Location** — physical or logical location
- **Hash** — SHA-256 (pre-computation if receiving, post-computation if transferring)
- **Notes** — any relevant observations (tool used, condition of evidence, exceptions)

Example:
```
timestamp: 2026-05-12T14:30:00Z
action: acquired
operator: forensic_analyst
evidence_item: case-001/source-disk1
location: /evidence/case-001/disk1.dd
hash_sha256: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
notes: dc3dd v7.3.1, source /dev/sdb, write-blocker Tableau T8u
```

## Hashing discipline

- Hash during acquisition (dc3dd integrated hashing)
- Hash after acquisition (independent verification with `sha256deep`)
- Hash before analysis (baseline)
- Hash after analysis (confirm no accidental modification)
- Hash before transfer (recipient's verification)
- Hash after transfer (sender's record)

Use strong hashes: SHA-256 minimum. MD5 can supplement but never substitute SHA-256.

For imaging, use `dc3dd` with `hash=sha256 hash=md5` to hash inline — this catches any read errors during acquisition.

For post-hoc verification:
- `sha256deep -r /evidence/case-001/ > case-001-hashes.sha256`
- Compare with acquisition hashes

## Working copy integrity

- Mount images read-only: `mount -o ro,noexec,loop image.dd /mnt/evidence`
- For E01: `ewfmount image.E01 /mnt/ewf` (creates a virtual raw file, no modification possible)
- If a tool requires read-write access, work on a copy of the copy

## Evidence transfer

When transferring evidence between systems or analysts:
- Package evidence in a verifiable container (tar, zip with hash manifest)
- Encrypt in transit (scp, rsync over SSH, encrypted USB)
- Recipient verifies hash before accepting
- Sender retains pre-transfer hash for dispute resolution

## Anti-tampering indicators

Signs of potential tampering to flag:
- Hash mismatch at any verification point
- Unexpected file modification timestamps
- Files with inconsistent metadata (creation > modification timestamps)
- Missing log entries in custody chain
- Evidence accessed outside documented windows
- System clock anomalies that undermine timestamp reliability

## Documentation standards

All chain-of-custody documentation lives alongside the evidence. In the YAML report, the `evidence_sources[].chain_of_custody` array captures every custody event. In the filesystem, keep a plain-text `CHAIN_OF_CUSTODY.log` in the evidence directory.

The custody log is itself evidence — hash it, timestamp it, and never modify prior entries. Append only.
